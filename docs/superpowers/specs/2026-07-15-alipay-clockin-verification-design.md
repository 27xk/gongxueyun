# 支付宝打卡安全验证设计

## 背景

工学云打卡接口可能返回 HTTP 成功且业务字段为 `code == 200`、`msg == "304"`。该响应不代表打卡成功，而是要求用户前往支付宝完成安全验证。现有调用链把所有未抛异常的 `code == 200` 响应视为成功，因此会错误记录“打卡成功”。

工学云同时提供支付宝验证登记接口：

- **请求方法：** `POST`
- **请求路径：** `usercenter/alipay/v1/createAxdjk`
- **认证方式：** 复用当前工学云认证请求头
- **请求体：** 仅包含加密时间戳字段 `t`

接口成功后返回 `outRegisterNo` 和 `registerUrl`。本次改动获取并返回这两个字段，但不会自动重试打卡。用户完成支付宝验证后，需要再次发起打卡。

## 目标

- 正确识别打卡接口的 `msg == "304"` 业务响应。
- 调用支付宝验证登记接口获取 `outRegisterNo` 和 `registerUrl`。
- 不自动重试打卡，避免在用户尚未完成验证时重复请求。
- 普通打卡和补卡均不得把待验证响应记录为成功。
- 通过任务结果的 `details` 保留验证信息，供当前或后续前端使用。
- 为用户端和管理端分别提供“验证完成，继续打卡”接口。
- 在两端前端提供支付宝验证对话框和显式继续按钮。
- 不在日志中输出认证头、完整请求体或 `registerUrl`。

## 非目标

- 不自动打开支付宝深链。
- 不轮询支付宝验证状态。
- 不新增数据库表或持久化待验证状态。
- 不新增全局 `pending` 任务状态。
- 不在用户完成验证后自动恢复原打卡任务。
- 不跨页面刷新保存登记信息。
- 不支持补卡任务在支付宝验证后的继续提交。

## 方案比较

### 方案一：返回业务结果（采用）

打卡提交方法返回结构化结果。正常响应返回成功结果，`304` 返回 `verification_required` 结果。任务执行层把后者映射为 `fail`，并在 `details` 中携带验证信息。

优点：业务分支清晰，不依赖异常传递数据；普通打卡和补卡可以复用；不需要扩展全局状态模型。

### 方案二：抛出自定义异常

为 `304` 定义携带 `outRegisterNo` 和 `registerUrl` 的异常，由任务执行层捕获。

缺点：需要用户操作属于预期业务状态，不适合用异常表示；URL 容易被通用异常日志意外记录。

### 方案三：新增 `pending` 状态并持久化

新增全局任务状态，保存登记信息并等待后续恢复。

缺点：会影响队列、通知、统计和多个前端页面，超出当前需求。

## 组件设计

### `ApiClient` 支付宝验证登记方法

在 `server/coreApi/MainLogicApi.py` 中新增专用方法，职责如下：

1. 使用 `_get_authenticated_headers()` 生成认证请求头。
2. 使用当前加密函数生成毫秒时间戳字段 `t`。
3. 通过 `_post_request()` 调用 `usercenter/alipay/v1/createAxdjk`。
4. 校验响应满足以下条件：
   - `code == 200`；
   - `msg == "success"`；
   - `data` 是对象；
   - `outRegisterNo` 是非空字符串；
   - `registerUrl` 是非空字符串。
5. 校验 `registerUrl` 使用 `alipays://` 协议，拒绝其他协议。
6. 返回仅包含 `outRegisterNo` 和 `registerUrl` 的结构化结果。

字段缺失或业务响应失败时抛出不包含敏感响应内容的 `ValueError`。

### 打卡提交方法

`_submit_clock_in_payload()` 只提交一次原始打卡请求，并根据业务响应处理：

- 正常成功：返回 `status == "success"`。
- `msg == "302"`：保持现有行为验证码处理流程。
- `msg == "304"`：调用支付宝验证登记方法，返回：

```json
{
  "status": "verification_required",
  "outRegisterNo": "登记编号",
  "registerUrl": "支付宝深链"
}
```

该分支不得自动发起第二次打卡。

显式继续打卡时，调用方把已经完成验证的 `outRegisterNo` 传入提交方法。提交方法将其写入新的打卡 payload，并只发送一次。若工学云再次返回 `304`，系统重新创建登记并返回最新验证信息。

`submit_clock_in()` 和 `submit_clock_in_replace()` 透传该结构化结果。

### 任务执行结果

`perform_clock_in()` 接收提交结果。遇到 `verification_required` 时立即返回：

```json
{
  "status": "fail",
  "message": "需要完成支付宝安全验证，请验证后重新打卡",
  "task_type": "打卡",
  "details": {
    "target_type": "START",
    "outRegisterNo": "登记编号",
    "registerUrl": "支付宝深链"
  }
}
```

任务不得继续执行“打卡成功”的日志和返回分支。普通打卡返回完整验证信息。补卡复用相同提交方法，因此也不得误报成功，但补卡结果不提供继续提交能力。

## 继续打卡 HTTP 接口

系统提供两个权限边界一致、业务实现共享的接口：

- 用户端：`POST /app/clock-in/alipay/continue`
- 管理端：`POST /users/{user_id}/clock-in/alipay/continue`

请求体如下：

```json
{
  "out_register_no": "登记编号",
  "target_type": "START"
}
```

请求字段约束：

- `out_register_no` 必须是非空字符串，长度和字符集按服务端白名单限制。
- `target_type` 只允许 `START` 或 `END`。
- 用户 ID、地址、Token、设备和计划信息不得由前端提交，统一从服务端绑定账户读取。
- 接口只继续当前普通打卡，不接受补卡日期或补卡标记。

用户端接口使用当前登录用户绑定的工学云账户。管理端接口沿用 `tasks:run` 权限和租户隔离规则。两端均复用现有手动打卡限流，并写入不含登记编号和深链的审计日志。

接口使用服务端配置重新构造打卡请求，把 `out_register_no` 映射为工学云 payload 的 `outRegisterNo`。响应返回单个标准任务结果：

```json
{
  "result": {
    "status": "success",
    "message": "上班打卡成功",
    "task_type": "打卡",
    "details": {}
  }
}
```

若继续打卡仍触发 `304`，`result` 再次返回 `fail` 和最新验证信息，前端更新当前对话框。

## 前端交互

新增共享支付宝验证对话框，并在用户端 `UserHome` 与管理端 `UserList` 的手动打卡入口复用。对话框显示明确的待验证状态，提供两个命令：

- **前往支付宝验证：** 使用后端返回且已校验的 `alipays://` 深链唤起支付宝。
- **验证完成，继续打卡：** 调用当前权限边界对应的继续接口。

前端从初次打卡任务结果的 `details` 读取 `outRegisterNo`、`registerUrl` 和 `target_type`，只保存在当前组件内存中，不写入 `localStorage`。继续请求期间禁用重复提交。成功后关闭对话框并刷新执行结果；再次触发验证时替换为最新登记信息；其他失败保留对话框并显示后端错误。

用户端调用 `/app/clock-in/alipay/continue`。管理端调用当前用户 ID 对应的 `/users/{user_id}/clock-in/alipay/continue`。共享组件不接触 Token 或用户 ID，仅通过事件把继续操作交给父页面。

## 数据流

1. 任务执行层组装打卡请求。
2. `ApiClient` 向工学云提交一次打卡。
3. 工学云返回 `msg == "304"`。
4. `ApiClient` 调用支付宝验证登记接口。
5. 登记接口返回 `outRegisterNo` 和 `registerUrl`。
6. `ApiClient` 返回 `verification_required`，不重试打卡。
7. 任务执行层返回 `fail` 结果及验证信息，前端打开验证对话框。
8. 用户通过深链完成支付宝验证。
9. 用户点击“验证完成，继续打卡”。
10. 前端调用对应继续接口，后端携带原 `outRegisterNo` 提交一次新打卡请求。
11. 成功时关闭对话框；再次返回 `304` 时更新登记信息并继续等待用户操作。

## 错误处理

- 登记接口网络失败：沿用 `_post_request()` 的超时、代理和 Token 刷新规则。
- 登记接口业务失败：返回“创建支付宝安全验证失败”。
- 响应缺少必需字段：返回“支付宝安全验证响应不完整”。
- 用户未完成验证：系统不轮询、不重试，继续操作只能由用户点击按钮触发。
- 显式继续打卡再次返回 `304`：重新创建登记并返回最新验证信息。
- 继续接口重复提交：受现有打卡记录检查和接口限流保护。

## 安全要求

- 测试和文档不得包含真实 Token、用户 ID 或登记编号。
- 日志不得输出认证头、打卡请求体、`outRegisterNo` 或 `registerUrl`。
- 通用异常信息不得拼接完整外部响应。
- `registerUrl` 仅通过任务结果 `details` 返回给已授权调用方。
- 后端仅接受 `alipays://` 协议的 `registerUrl`，不得把任意外部 URL 交给前端打开。
- 审计日志不得记录 `out_register_no` 或 `registerUrl`。

## 测试设计

新增或扩展单元测试，覆盖以下场景：

1. 登记接口使用正确路径、认证请求头和加密时间戳字段。
2. 登记接口正确提取两个返回字段。
3. 登记接口缺少字段时明确失败。
4. 首次打卡返回 `304` 时只调用一次打卡接口和一次登记接口。
5. 初次 `304` 分支不携带 `outRegisterNo` 自动重试打卡。
6. 普通成功响应仍返回成功。
7. 任务执行层把待验证结果映射为 `fail`，并保留普通打卡的验证信息。
8. 普通打卡和补卡均不会误报成功，补卡不进入继续打卡流程。
9. 日志和异常断言不包含完整 `registerUrl`。
10. 两个继续接口分别验证用户绑定关系、管理权限和租户隔离。
11. 继续接口拒绝非法登记编号和非法打卡类型。
12. 继续打卡 payload 包含 `outRegisterNo`，且只提交一次。
13. 前端识别验证结果并打开共享对话框。
14. 两端前端调用各自的继续接口，并正确处理成功、再次验证和普通失败。

## 影响范围

- `server/coreApi/MainLogicApi.py`：新增登记接口并调整打卡业务结果。
- `server/task_runner.py`：识别待验证结果并返回任务详情。
- `server/api.py`：新增用户端和管理端继续打卡接口。
- `web/src/components/AlipayVerificationDialog.vue`：提供共享验证交互。
- `web/src/views/user/UserHome.vue`：接入用户端验证结果和继续接口。
- `web/src/views/UserList.vue`：接入管理端验证结果和继续接口。
- 后端单元测试：覆盖接口、分支、错误处理和任务结果。

不修改数据库结构和任务状态枚举。
